# 06. 기존 서비스 통합 체크리스트

## 1. 권장 통합안

### 1차: API 어댑터 통합

기존 서비스의 화면·메뉴·인증 컨텍스트 안에서 GJU 기능을 호출하되, 예약 도메인과 데이터는 현재 Worker·Durable Object에 유지한다.

장점:

- 예약 충돌·상태 전이 규칙을 재구현하지 않는다.
- 기존 운영 데이터를 바로 사용할 수 있다.
- 장애 시 GJU 기능만 분리해 롤백할 수 있다.
- 데이터 마이그레이션 없이 사용자 흐름을 먼저 검증할 수 있다.

### 2차: 인증·UI 통합

- 기존 서비스 사용자와 GJU 사용자를 명시적으로 연결한다.
- 기존 서비스의 공통 헤더·내비게이션·디자인 토큰을 적용한다.
- 로그인 토큰 교환 또는 BFF 세션을 도입한다.
- 관리자 접근을 기존 서비스 권한과 연결한다.

### 3차: 데이터 통합

충분한 병행 운영과 데이터 비교 후에만 기존 서비스 DB로 정규화 이관한다. 이 단계에서는 수요조사 응답, 예약 이력, 보고서, 감사 로그 보관 정책을 별도 승인한다.

## 2. 시스템 경계 결정

통합 착수 전에 다음 소유권을 문서로 확정한다.

| 항목 | 선택 |
| --- | --- |
| 사용자 원장 | 기존 서비스 / GJU |
| 로그인·비밀번호 | 기존 서비스 / GJU |
| 학생 승인 상태 | 기존 서비스 / GJU |
| 기자재 마스터 | 기존 서비스 / GJU |
| 예약 원장 | GJU 권장 |
| 보고서 원장 | GJU 또는 기존 파일 시스템 |
| 특강·공지 | 기존 서비스와 중복 여부 결정 |
| 수요조사 과목 마스터 | 학과 GJU 관리 권장 |
| 수요조사 응답 | 접근 권한이 제한된 학과 데이터 |
| 운영 통계 | GJU 관리자 화면 |
| 알림 | Slack·로컬 알림 유지 또는 기존 알림으로 대체 |

하나의 엔터티에 두 쓰기 원장을 두지 않는다. 예를 들어 기자재 상태를 기존 서비스와 GJU 양쪽에서 수정하도록 두면 예약 가능 판정이 어긋난다.

## 3. 인증 연동

### 선택지 A: GJU 로그인 유지

- 기존 서비스 메뉴에서 GJU 화면으로 이동한다.
- GJU 토큰과 세션을 독립적으로 유지한다.
- 개발량은 작지만 사용자는 별도 로그인해야 한다.

### 선택지 B: 토큰 교환

권장 흐름:

1. 사용자가 기존 서비스에 로그인한다.
2. 기존 서비스 백엔드가 사용자 ID·학번·권한을 검증한다.
3. 기존 서비스 백엔드가 GJU 연동 엔드포인트에 서명된 요청을 보낸다.
4. GJU가 기존 사용자와 연결된 내부 `user.id`를 찾거나 생성한다.
5. 짧은 수명의 GJU 세션 또는 교환 코드를 반환한다.
6. 브라우저는 원본 비밀번호 없이 GJU 기능을 사용한다.

현재 코드에는 토큰 교환 API가 없으므로 별도 구현이 필요하다.

### 선택지 C: 기존 인증으로 완전 교체

- `requireUser`, `requireApprovedStudent`, `requireAdmin` 앞단을 기존 JWT·세션 검증으로 교체한다.
- 내부 도메인 함수의 승인·소유자·역할 검사는 유지한다.
- 기존 서비스 사용자 ID와 GJU 데이터의 연결을 보장한다.

### 필수 인증 체크

- [ ] 기존 사용자 ID와 GJU `user.id`의 매핑 방식 확정
- [ ] 이메일·학번 중복 처리 정책 확정
- [ ] 졸업·휴학·복학 상태 동기화 방식 확정
- [ ] 승인·대여금지 상태의 원장 확정
- [ ] 관리자 역할 매핑 확정
- [ ] 토큰 만료·로그아웃·세션 회수 동작 확정
- [ ] 계정 삭제가 기존 서비스 계정까지 삭제하는지 범위 확정

## 4. 라우팅·프론트 통합

### 권장 경로

```text
/department/photo-reservation
/department/photo-reservation/admin
/api/gju-reserve/*
```

기존 서비스 게이트웨이가 `/api/gju-reserve/*`를 GJU Worker `/api/*`로 변환할 수 있다.

### 확인

- [ ] SPA fallback 충돌 없음
- [ ] 정적 자산 경로가 기존 서비스 자산과 충돌하지 않음
- [ ] GJU React 번들 로드 순서 확인
- [ ] `window.GJU_API_BASE`를 새 프록시 경로로 설정
- [ ] CSP `connect-src`, `script-src`, `style-src`, `img-src` 조정
- [ ] 새 도메인을 Worker CORS에 추가
- [ ] 모바일 safe area와 기존 하단 메뉴 중복 방지
- [ ] 로그인·로그아웃 시 두 서비스 상태 일치
- [ ] 새로고침·뒤로가기·딥링크 확인

### 학생 화면 우선순위

1. 홈: 수요조사, 예약 바로가기, 다음 예약
2. 예약: 4종 예약
3. 내 예약
4. 보고서
5. 특강
6. 공지
7. 마이

수요조사는 학생 홈에서 확인·응답할 수 있어야 한다. 별도 깊은 메뉴에만 두지 않는다.

### 관리자 화면 우선순위

1. 대시보드
2. 학생 승인
3. 예약 관리
4. 기자재
5. 보고서
6. 교과 수요조사
7. 특강·공지
8. 로그·설정

공식 편성안 작성 화면은 통합 대상에서 제외한다.

## 12. 최종 완료 기준

통합은 다음이 모두 확인되면 완료로 본다.

- 학생이 기존 서비스 로그인 상태에서 GJU 기능에 접근한다.
- 승인·차단·소유자·관리자 권한이 우회되지 않는다.
- 4종 예약 규칙과 충돌 검사가 동일하게 동작한다.
- 즐겨찾기·재예약·대안 추천이 동작한다.
- 학생 홈에서 대상 수요조사를 확인하고 1~5순위 응답을 저장한다.
- 관리자가 설문안을 만들고 5~6개 후보를 공개하며 결과를 집계한다.
- 관리자 대시보드의 정량 지표가 기준 데이터와 일치한다.
- 개인정보 방침, 계정 삭제, 보관정책이 유지된다.
- 웹·iOS·Android 또는 선택된 대상 플랫폼의 QA가 통과한다.
- 백업·전환·롤백 절차가 실제로 한 번 검증된다.
