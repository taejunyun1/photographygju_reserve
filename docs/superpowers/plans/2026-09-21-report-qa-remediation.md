# 보고서 기능 실질 QA 후 수정·배포 계획

작성일: 2026-09-21

## 1. 목표와 범위

학생이 스튜디오·기자재 사용 보고서를 작성하고 사진을 최대 5장 첨부하여 안전하게 제출한다. 관리자는 앱에서 내용과 사진을 확인하고 Google Drive 보관 상태를 확인한다.

새 기능을 추가하는 계획이 아니라 기존 승인 요구의 누락과 재현 오류를 바로잡는 계획이다. 이번 작업은 계획 문서 작성에 한정한다. 코드 수정·운영 DB 변경·커밋·스토어 업로드는 하지 않는다.

기존 `2026-09-21-report-photos-google-drive.md`의 요구를 유지하되, 작업 순서와 완료 판정은 이 문서를 따른다. 모든 수정은 메인 작업자가 순서대로 진행한다. 반복적인 서브에이전트 검증은 하지 않는다.

## 2. 현재 판정: 배포 보류

격리된 메모리 DB와 실제 API 처리 함수에 PNG 바이너리를 전달하여 아래 오류를 재현했다. 운영 계정·운영 보고서를 변경하지 않았다.

| 항목 | 재현 결과 | 영향 |
| --- | --- | --- |
| 초안 사진 복구 | 5장 업로드 후 재조회 결과 0장 | 학생이 첨부를 잃었다고 판단하고 재업로드할 수 있음 |
| 제출 후 사진 삭제 | 삭제 요청 성공, 사진 상태 deleted | 제출 증빙 변경 가능 |
| 동일 제출 재시도 | 최초 성공 후 동일 키 요청은 400 | 응답 유실 시 학생에게 실패로 안내 |
| 미래 스튜디오 예약 | 2099년 예약도 현재 작성 대상으로 반환 | 대시보드·보고서 대상 집계 오류 |
| 과거 기자재 반납 | 새 정책 없는 과거 반납 건에도 의무 생성 | 소급 미제출 집계 |
| Drive 부분 성공 | JSON 저장 후 HTML 실패 시 JSON 파일 ID 미보존 | 재시도 중복 생성 위험 |

통과: 사진 5장 업로드, 6번째 차단, 최초 제출. 기존 화면 테스트 8개는 통과했으나 제출 응답을 모의 처리하므로 신규 저장 경로의 완료 증거가 아니다. `npm run test:reporting`도 현재 실패하며 요구와 테스트 기대값을 함께 검토해야 한다.

Drive 오류는 가짜 클라이언트로 장애를 주입해 확인했다. 실제 Google 계정 저장, iPhone 실기기, 운영 배포는 검증하지 않았다.

## 3. 수정 순서

### 1단계 — 제출 데이터 보호와 재시도: 최우선

대상: `core.mjs`, `public/js/react-student-adapter.js`, 관련 API 테스트.

1. 초안 사진 조회에 초안 객체가 아니라 `draft.id`를 전달한다. 삭제된 첨부만 제외하고 업로드 상태를 일관되게 반환한다.
2. 제출된 초안의 수정·사진 예약·바이너리 덮어쓰기·삭제를 공통 검사로 차단한다. 본인 요청이어도 최종 제출본을 변경할 수 없다.
3. 클라이언트의 제출 키를 재시도 동안 유지하고 서버 보고서에도 저장한다. 동일 키·동일 요청은 기존 성공 결과를 반환하며 다른 내용의 키 재사용은 충돌로 처리한다.
4. 이미 제출한 요청인지 먼저 확인한 뒤 신규 제출 자격을 검사한다. 다른 키로 재요청하더라도 예약·유형별 최종 보고서는 하나만 생성한다.
5. DB 저장 실패 시 메모리의 제출 상태·사진 연결·작업 생성도 되돌린다. 동시 제출·동시 첨부 요청의 원자성과 유일성도 보장한다.

완료 조건: 초안 복구 5장, 모든 제출 후 변경 거부, 응답 유실·동시 제출에서도 보고서 1개, 저장 실패 후 재시도 가능, 동시 업로드에서도 총 5장 이하.

### 2단계 — 작성 대상·마감·카운트 통일

대상: `core/reporting.mjs`, `core/reservation-timing.mjs`, 예약 API, 학생 대시보드·보고서 목록, 관리자 집계, 알림.

1. 기존 예약 시간 계산 함수를 사용한다. 시작 시각 누락을 1970년으로 처리하거나 정상 슬롯을 날짜 말일로 대체하지 않는다.
2. 스튜디오는 사용일 도래 시 작성, 실제 슬롯 종료 또는 관리자 완료 처리 후 제출한다. 야간·자정 이후 슬롯을 포함한다. 시간 자료가 잘못된 예약은 임의로 의무를 부과하지 않고 확인 필요로 분리한다.
3. 기자재는 인계 완료부터 대상이다. 기능 활성화 당시 대여 중 건과 이후 인계되는 건에 정책 버전을 기록하고, 기존 반납 완료 건은 소급하지 않는다. 활성화 시각·대상 수를 기록해 반복 실행해도 결과가 같게 한다.
4. 기자재 마감은 예정 반납과 실제 조기 반납 중 빠른 시각을 기준으로 한다. 지연 반납으로 마감이 연장되지 않는다. 기한 초과 제출은 허용한다.
5. 공통 판정으로 학생 작성 필요 수·목록·알림을 계산한다. 관리자 지표는 ‘학생 미제출’과 ‘접수 후 관리자 미확인’을 별도로 정의한다. 같은 이름의 지표·목록은 동일한 기간과 상태 필터를 쓴다.

완료 조건: 미래·취소·반려·인계 전·과거 반납 건 제외, 정상 인계·반납 포함, 조기/지연 반납·야간 경계 통과, 각 카드 클릭 결과의 총건수와 카드 숫자 일치.

### 3단계 — 작성·임시저장·열람 흐름 완성

대상: `ReportForm.tsx`, `ReportPhotoPicker.tsx`, `ReportsScreen.tsx`, 학생 어댑터, `AdminReports.tsx`.

1. 스튜디오 파손 O/X와 실제로 연결한 본인 대여 기자재의 O/X를 구분한다. 대여가 없으면 없음으로 표시한다. 날짜만으로 자동 연결하지 않는다.
2. 필수 O/X는 미선택 상태로 시작한다. 파손 O에는 해당 구분의 설명과 사진이 필수다. 서버가 실제 적용 구분을 판정하고 클라이언트 `_legacy` 값으로 검증을 우회하지 못하게 한다.
3. 임시저장 버튼과 저장 상태를 제공한다. 제출 전 시각에는 임시저장만 가능하다고 표시한다. 새로고침·앱 재시작 후 텍스트와 사진을 복구하고 미전송/저장완료를 구분한다.
4. 사진 처리와 전송을 순차화하고 중복 선택 경쟁을 막는다. 전체 구분 합계 5장 제한, 실패 사진별 재시도, 명시적 삭제를 지원한다.
5. 학생 제출 완료 상세와 관리자 상세에서 사진을 실제로 열어 볼 수 있게 한다. 사진 수만 보여 주는 것으로 완료 처리하지 않는다. 다른 학생의 보고서·사진은 서버에서 차단한다.
6. 새 화면은 신규 API를 일관되게 사용한다. 구버전 앱의 기존 제출 API는 별도 호환 경로로 보존하고 회귀 검증한다.

완료 조건: 학생 작성→임시저장→복구→제출→학생 상세→관리자 사진 열람을 실제 API 연결 브라우저에서 수행한다. 파손 없음/있음, 스튜디오 단독/대여 연결/기자재 단독을 포함한다.

### 4단계 — 사진 저장·Drive 복구 안정화

대상: `integrations/report-drive.mjs`, `integrations/report-drive-jobs.mjs`, `storage-sql.mjs`, `worker.mjs`, Drive 설정 API·화면.

1. 기존 승인안대로 신규 사진 바이너리를 DB JSON/base64에 쌓지 않는다. DB는 첨부 메타데이터를 보관하고 사진은 Drive에 저장한다. 전송 전 자료는 계정별 기기 임시저장으로 보호한다.
2. 이미 저장된 base64 첨부가 있는지는 읽기 전용으로 먼저 조사한다. 존재하면 개수·용량을 확인하고 이관 성공 및 파일 무결성 확인 전 원본을 제거하지 않는다.
3. 파일 ID와 업로드 작업을 외부 요청 전에 영속화하고 같은 ID로 재시도한다. 업로드 응답 유실 시 원격 파일을 조회·검증한다. 폴더 생성도 재사용/중복 방지 규칙을 둔다.
4. 접수 상태와 Drive 저장 상태를 분리한다. 사진이 저장되었다면 요약 저장 실패 때문에 재제출시키지 않는다. 필수 사진이 미전송이면 제출 완료로 표시하지 않는다.
5. 모든 API 요청에 Drive 재시도를 붙이지 않는다. 영속 작업과 Durable Object alarm으로 처리하며 재시도 간격·상한·복구 필요 상태를 둔다.
6. OAuth state를 연결을 시작한 관리자 세션에 묶어 일회성·만료·권한을 검사한다. 연결 확인은 실제 폴더 읽기·쓰기 가능 여부를 검증한다. 검사용 파일만 정리한다.
7. 작업·첨부를 원래 연결 계정에 고정한다. 계정 변경 시 이전 자료를 새 계정에 자동 전송하지 않는다. 재연결 필요와 일시 장애를 구분한다.
8. 요약 HTML/JSON에 점검 구분·예약 정보·첨부를 완전하게 반영하고 HTML을 escape한다. 보관기간 안내와 앱/Drive 삭제·재시도 정책의 일치 여부도 확인한다. 원격 삭제는 지정 대상에 한정하고 별도 검증 전 활성화하지 않는다.

완료 조건: 부분 성공·응답 유실·서버 재시작에도 중복 파일 없음, 접속자가 없어도 재시도 진행, 다른 계정으로 잘못 전송 없음, 실제 연결 계정에서 보고서와 사진 열람 성공. 연결 계정·테스트 폴더가 없으면 외부 연동 검증 미완료로 명시한다.

### 5단계 — 통합 QA와 배포

각 단계에서 재현 실패 테스트를 먼저 고정하고 해당 수정 범위만 검증한다. 마지막에 통합 QA를 한 번 수행한다. 성공 응답을 모의로 교체한 화면 테스트는 별도 분류한다.

| 검증층 | 필수 항목 |
| --- | --- |
| 도메인/API | 위 6개 재현 오류, 권한, 동시성, DB 실패, 날짜 경계, 구버전 호환 |
| 실제 API 브라우저 | 학생 작성·5장 첨부·임시저장 복구·제출·관리자 원본 열람, 모바일/PC, 콘솔 오류 |
| 실제 Drive | 승인된 테스트 계정/폴더에 쓰기·읽기, 재시도 파일 수와 ID 확인, 연결 해제·재연결 |
| 네이티브 | iPhone 촬영/사진 선택·권한 거부·복귀·앱 종료 복구·업로드, Android 대응 회귀 |
| 운영 스모크 | 배포된 프런트/백엔드 버전 일치, 구버전 앱 호환, 테스트 계정으로 제출·관리자 확인 |

`test:reporting`을 정식 release 검증에 포함하고 필수 검사 실패 시 배포하지 않도록 한다. 실제 Drive나 기기 검증을 실행하지 못했다면 통과로 처리하지 않는다.

배포 순서:

1. 운영 스키마·현재 첨부 현황 확인, 백업/복구 절차 준비, 마이그레이션 dry-run.
2. 자동 QA와 테스트 환경 외부 연동 QA 통과.
3. 하위 호환 백엔드 배포 → 프런트 배포 → 운영 스모크 테스트.
4. 최신 App Store Connect 빌드 번호 확인 → iOS 패키징·서명 → 업로드 → 처리 완료 확인.
5. 업로드/TestFlight 처리 완료와 App Store 심사·일반 공개 상태는 구분해 보고한다. 운영 스모크 실패 시 네이티브 업로드를 중단한다.

롤백은 이전 프런트/백엔드 버전 복귀를 우선하되 새로 접수된 보고서·첨부·작업을 삭제하지 않는다. 이전 버전이 새 데이터를 보존·해석할 수 있는지 배포 전 확인한다.

## 4. 최종 완료 기준

- 재현된 6개 오류의 회귀 테스트 통과.
- 최종 제출본 변경 불가, 응답 유실 후 재시도 안전, 데이터 저장 실패 복구 가능.
- 학생·관리자 숫자와 해당 목록의 기준 일치.
- 앱에서 작성·복구·제출·사진 열람을 끝까지 수행 가능.
- 실제 Drive 저장·조회·중복 방지 검증 완료.
- iPhone 실기기 핵심 흐름 검증 완료.
- 운영 배포 버전 확인 및 App Store Connect 처리 상태 기록.

완료 보고에는 테스트 환경, 실행 수/실패/미실행, 수정 커밋, 배포 버전, iOS 빌드 번호를 남긴다. 코드가 존재하거나 화면이 뜨는 것만으로 구현 완료라고 보고하지 않는다.
