# 보고서 사용자 흐름 완성·업데이트 구현 계획

> **실행 방식:** 메인 작업자가 `superpowers:executing-plans` 방식으로 아래 작업을 순서대로 수행한다. 사용자 선호에 따라 서브에이전트 반복 검증을 추가하지 않는다. 단계별 검증 후 마지막 통합 QA를 한 번 진행한다.

**Goal:** 학생이 앱에서 보고서를 작성하고, 중단 후 복구하고, 안전하게 제출한 뒤 내용·사진을 다시 확인하며, 관리자가 앱과 Google Drive에서 같은 제출본을 확인한다.

**Architecture:** 서버의 보고서 대상·접수 상태를 학생 목록과 관리자 집계의 공통 기준으로 삼는다. 기존 초안·첨부 API를 보완하고 작성 화면·학생 상세·관리자 사진 열람을 연결한다. 접수와 Drive 보관 상태를 구분하고, 업로드 전 자료는 계정별 로컬 저장소에서 보호한다.

**Tech Stack:** React/TypeScript, 기존 JavaScript 어댑터, Node 로컬 서버, Cloudflare Worker와 SQLite Durable Object, Google Drive 연동, Capacitor iOS/Android, Playwright.

## 범위와 현재 기준

- 작성일: 2026-09-21. 기준 커밋: `57601c8`. 기존 수정계획 `2026-09-21-report-qa-remediation.md` 이후의 남은 작업을 이 문서로 관리한다.
- 이번 실행에서는 학생 보고서 작성 흐름과 서버 조회 계약을 구현하고 로컬 QA 및 웹 배포까지 진행한다. 실제 운영 Google Drive/OAuth 연결과 스토어 업로드는 외부 계정·심사 조건 때문에 별도 확인 대상으로 남긴다.
- 이미 반영된 초안 사진 목록 ID 수정, 서버 동일 키 응답, 제출된 초안 잠금, 일부 시간 계산, Drive 부분 성공 ID 기록을 보존한다. 이를 전체 사용자 흐름 완료로 간주하지 않는다.
- 기존 실제 브라우저 검증은 기자재 보고서 사진 1장 최초 제출이다. 임시저장·중단 복구·응답 유실·학생 상세·관리자 사진 확인은 새 검증 대상이다.
- 사진은 보고서 전체 합계 최대 5장. 파손 O인 각 구분에는 상세 1~2,000자와 사진 최소 1장. X일 때 사진은 선택이다. O/X 초기값은 미선택이다.
- 예약명·날짜·장비명·코드는 자동 표시한다. 새로운 통계나 별도 메뉴를 늘리지 않고 기존 홈·보고서·관리자 설정을 확장한다.
- 학생에게 Google 로그인·Drive 폴더 공유를 요구하지 않는다. 관리자가 설정에서 보고서 전용 저장 계정과 폴더를 확인한다.
- 기존 보고서·사진 링크와 구버전 앱 제출 API를 유지한다. 파손 O만으로 재고·패널티를 자동 변경하지 않는다.
- 작성 초안 7일, 제출 자료 183일은 기존 계획의 기본안이다. 실제 설정·개인정보 안내·삭제 실행 조건을 일치시켜 활성화한다.

## 1. 완성할 학생 UX

홈 `작성할 보고서 N건` 또는 하단 `보고서` → 예약별 `작성/이어서 작성` → O/X와 사진 → `임시저장/제출` → `제출 내용 보기`.

기존 보고서 화면에서 작성 폼을 연다. 폼을 열면 제목 위치로 이동하고 포커스를 옮긴다. 모바일에서는 하단 버튼이 내비게이션·키보드와 겹치지 않도록 한다. 별도 다단계 마법사는 만들지 않는다.

| 단계 | 학생에게 보이는 내용 | 동작 |
| --- | --- | --- |
| 진입 | 작성 필요 / 작성 중 / 제출 완료 | 작성 중에는 마지막 저장 시각과 이어서 작성 표시 |
| 예약 정보 | 사용일·공간 또는 대여 장비 | 서버 예약 정보 자동 표시 |
| 스튜디오 점검 | 스튜디오 기자재·시설 O/X | 스튜디오 보고서에서만 필수 |
| 대여 점검 | 대여 기자재 O/X | 기자재 보고서에서는 필수. 스튜디오에서는 연결한 대여가 있을 때 표시 |
| 대여 연결 | 별도 대여 없음 / 내 대여 예약 선택 | 본인의 실제 인계 이력이 있는 예약을 선택. 날짜만으로 자동 연결하지 않음 |
| 사진 | 전체 2/5장, 구분, 미리보기, 삭제 | 파손 구분마다 필수 사진 여부 안내 |
| 확인 | 정리정돈 또는 기자재·구성품 상태 체크, 선택 비고 | 스튜디오는 사용 시간·인원 확인도 포함 |
| 저장 | 기기에 저장됨 / 서버에 저장됨 / 저장 실패 | 저장 성공한 범위를 정확히 표시 |
| 제출 | 사진 전송 중 / 제출 확인 중 / 접수 완료 | 연타 차단, 불확실한 응답은 기존 접수 여부 확인 |
| 제출 이후 | 내용 보기 → 예약·O/X·설명·사진·제출 시각 | 읽기 전용. 접수와 관리자 확인 상태 표시 |

스튜디오에 대여 예약을 연결해도 해당 기자재 예약의 보고서가 자동 제출되지는 않는다. 연결은 관련 기록을 찾아보는 용도이다.

### 중단·실패 시 사용자 동작

- 입력을 멈춘 뒤 800ms 후 기기에 자동 보존한다. 사진은 파일 저장이 성공한 뒤 저장 표시를 바꾼다. 저장 장치 오류 시 성공 표시를 하지 않는다.
- `임시저장`은 서버 초안 저장 및 사진 전송을 시도한다. 일부 사진만 성공하면 `내용 저장됨 · 사진 1장 전송 필요`처럼 표시한다.
- 닫기·다른 메뉴 이동 시 로컬 보존을 완료한다. 미보존 자료가 있을 때만 이탈 확인을 표시한다. 새로고침·앱 종료 후 같은 계정으로 열면 복구한다.
- 정상 로그아웃 시 미전송 자료가 있음을 알리고 서버 전송 또는 명시적 폐기를 선택하게 한다. 로그아웃 완료 후 그 계정의 로컬 자료를 정리한다. 세션 만료는 다른 계정에 표시하지 않고 동일 계정 재로그인 후 복구한다.
- 사진 선택·변환·업로드는 전체 보고서에서 하나의 큐로 처리한다. 두 구분에서 동시에 선택해도 5장을 넘지 않는다.
- 사진 변환·전송 실패는 해당 항목에 재시도를 표시한다. 학생이 지운 첨부는 서버 초안에서도 제거하며, 응답 유실로 다시 나타나지 않도록 삭제 상태를 동기화한다.
- 최종 제출 가능 시각 전에는 `임시저장`을 활성화하고 제출 버튼 옆에 가능한 시각을 표시한다. 기한이 지나도 제출할 수 있다.
- 이미 접수된 경우 재업로드·초안 수정 없이 제출 상세로 이동한다. 아직 접수되지 않았다면 저장된 제출 키와 같은 요청으로 재시도한다.

## 2. 관리자 UX

- 보고서 목록의 `확인 대기`에서 상세를 열고 예약 정보, 구분별 점검, 사진 썸네일·확대 보기를 확인한다.
- 기자재 보고서에는 ‘정리 확인’ 대신 ‘기자재·구성품 확인’을 표시한다. 스튜디오/기자재 유형에 맞지 않는 항목은 숨긴다.
- `확인 완료` 처리 후 학생 상세에도 확인 상태가 반영된다. 이미 제출된 내용과 증빙은 수정하지 않는다.
- Drive 상태는 폴더 링크 유무와 독립적으로 항상 표시한다. `저장 대기/저장 중/저장 완료/연결 확인 필요`와 실패 항목의 재시도를 제공한다.
- 관리자 설정에서 계정·폴더·연결 확인·마지막 성공·대기/실패 건수를 확인한다. Google 최초 연결은 관리자 웹에서 수행한다.
- 학생 미제출 수와 관리자 확인 대기 수는 별도 지표이다. 카드 클릭 시 해당 목록 총건수와 동일해야 한다.

### 상태·API 계약

`required=false`가 있으면 프런트는 예전 규칙으로 다시 true로 바꾸지 않는다. `deadlineAt`은 서버 값을 우선한다. 구버전 응답에 필드가 아예 없을 때만 명시된 호환 규칙을 사용한다.

```ts
type ReportSaveState = "dirty" | "saving_local" | "local_saved" | "saving_server" | "server_saved" | "failed";
type ReportSubmitState = "idle" | "uploading" | "submitting" | "confirming" | "submitted" | "failed";
type LocalDraftKey = { userId: string; reservationId: string };

// 기존 StudentReportDraft / StudentReportPhoto 확장
// submittedAt, submissionKey, revision, updatedAt, clientPhotoId,
// 저장 위치와 업로드 상태를 가진다. 인증 토큰은 저장하지 않는다.

// StudentActions에 추가. 기존 submitReport는 유지한다.
saveReportDraft(id: string, payload: StudentReportPayload): Promise<StudentReportDraft>;
loadReportDetail(reportId: string): Promise<AdminReportRecord>;
loadReportPhoto(reportId: string, photoId: string): Promise<{ data: string; mimeType: string }>;
```

- `GET /api/reports/my`: 작성 대상·초안·제출 목록을 일관되게 반환한다. 반환된 제출본으로 응답 유실을 확인한다.
- `POST /api/reports/drafts`: 본인 예약의 기존 초안을 재사용한다. 제출본이 존재하면 `reportId`, `submittedAt`을 포함해 편집 대신 상세로 안내한다.
- `PATCH /api/reports/drafts/:id`: revision을 검사하고 허용된 입력만 저장한다. 충돌은 409로 반환하고 기기 입력을 보존한다.
- 사진 예약/전송/삭제 API: 본인 소유권, 최종 제출 잠금, 유형·크기·5장 제한을 공통 검사한다. 사진 변경도 초안 revision에 반영한다.
- `GET /api/reports/drafts/:id/photos/:photoId/content` (신규): 본인 미제출 초안의 업로드 완료 사진을 복구한다.
- `POST /api/reports/drafts/:id/submit`: 초안 revision·사진 목록·내용으로 고정한 동일 제출 요청만 재시도한다. 동일 키로 다른 내용을 보내면 409. 접수 완료 확인은 일반 조회로 처리한다.
- `GET /api/reports/:id` (신규), 기존 `GET /api/reports/:id/photos/:photoId/content`: 본인 또는 관리자만 읽는다. 응답은 private/no-store, 공개 사진 URL과 토큰 포함 링크는 만들지 않는다.
- 새 화면은 신규 제출 API를 일관되게 사용한다. 기존 `/api/reports/studio`의 호환 여부는 서버 라우트가 결정하고 입력 `_legacy`로 신규 검증을 우회하지 못한다.

### 작업 3 — 사진 저장 및 Drive 작업 계약 완성

로컬 저장 UI를 연결하기 전에 업로드 완료의 의미를 확정한다. 기존 승인안인 ‘사진은 Drive, DB는 메타데이터’를 유지한다.

- [ ] `scripts/report-drive-jobs-test.mjs`를 추가하여 JSON만 성공/사진 일부 성공/응답 유실/프로세스 재시작/연결 계정 변경을 검증한다.
- [ ] 파일 식별자·connectionId·작업 상태를 외부 쓰기 전에 영속화한다. 폴더·사진·요약의 원격 존재를 확인하고 같은 작업의 재시도로 중복 생성하지 않는다. 기존 파일 갱신 시 생성 전용 메타데이터를 그대로 보내지 않는다.
- [ ] 신규 사진 바이너리를 DB JSON/base64에 저장하지 않는다. 기존 자료 이관은 개수·용량 조사와 무결성 검증을 거쳐 수행하고 확인 전 원본을 제거하지 않는다. 로컬 QA용 저장 대역은 테스트에서만 주입한다.
- [ ] 사진이 Drive에 저장된 후 첨부를 완료 처리한다. 아직 저장하지 못한 필수 사진이 있으면 최종 제출을 보류하고 기기에 보존한다. 사진 없는 보고서는 접수 후 요약 저장 대기가 가능하다.
- [ ] 요약 작업은 Durable Object alarm에서 실행한다. 접속자가 없어도 재시도하며, 임시 오류는 1분/5분/30분/2시간 간격, 인증·권한 오류는 관리자 복구 필요로 표시한다. 모든 API 요청에서 외부 업로드를 실행하는 기존 경로를 제거한다.
- [ ] OAuth state의 관리자 세션 연결·일회성·만료를 검사한다. 연결 확인은 지정 폴더의 읽기/쓰기 검증을 포함한다. 이전 자료의 connectionId를 새 계정에 자동 변경하지 않는다.
- [ ] 요약 HTML/JSON에 양쪽 점검과 예약·사진 참조를 담고, 앱에서 권한 검사 후 사진을 열람하게 한다. 로컬/Drive 보관 만료·삭제 실패 재시도를 기록하고 기존 안내와 맞춘다.
- [ ] `node scripts/report-drive-jobs-test.mjs`를 통과시키고 `package.json`의 release 검사에 포함한다. 실제 계정 저장은 최종 외부 QA에서 별도 확인한다.

## 5. 배포 순서와 완료 기준

1. 실제 연결 가능한 QA Drive 계정·전용 폴더로 사진·요약 읽기/쓰기를 확인하고, iPhone에서 촬영·선택·권한 거부·앱 재시작 복구를 검증한다. 연결 대상이 없으면 필요한 계정/폴더만 확인 요청한다.
2. 운영 데이터·첨부 수·정책 버전 조사, 백업·복원 가능성 확인, 마이그레이션 dry-run 후 하위 호환 백엔드를 배포한다.
3. 프런트 배포 시 캐시 버전을 갱신하고 실제 서비스의 프런트/백엔드 버전을 확인한다. 구버전 설치 앱의 보고서 제출도 확인한다.
4. 운영 QA 계정으로 제출→관리자 사진 확인을 수행한다. 성공하면 최신 빌드 번호로 패키징하고 App Store Connect 업로드·처리 완료를 확인한다. 심사 제출/승인/일반 공개는 업로드 완료와 구분한다.
5. Android도 같은 웹 자산과 사진 권한·복구 동작을 검증한다. Play Console 테스터 조건은 별도 배포 제약으로 기록한다.

되돌림은 새 데이터·첨부를 보존하는 버전 복귀를 기본으로 한다. 이전 버전이 새 데이터 형태를 읽고 보존할 수 있는지 먼저 확인한다. 실제 사용자 보고서를 QA 목적으로 삭제하지 않는다.

‘완료’는 학생의 작성→저장→중단→복구→제출→상세 확인과 관리자의 동일 증빙 열람이 연결됐을 때만 사용한다. 로컬 QA 완료, 실제 Drive 완료, 실기기 완료, 운영 배포, App Store Connect 처리를 각각 증거와 함께 보고한다.
